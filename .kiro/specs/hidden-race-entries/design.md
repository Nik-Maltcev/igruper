# Скрытие заявок соперников — Дизайн исправления бага

## Обзор

В компоненте `RaceCenter.tsx` подкомпонент `EntryButton` отображает блок «Стартовая решётка» с именами игроков и названиями их машин ещё на этапе записи (фаза `RACE_DAY`). Это нарушает правила игры — выбор машины должен быть скрыт до старта гонки. Исправление заменяет детальный список заявок соперников на простой счётчик «Записано: N», сохраняя при этом отображение собственной заявки игрока.

## Глоссарий

- **Bug_Condition (C)**: Условие, при котором проявляется баг — фаза `RACE_DAY` и наличие заявок других игроков (`otherEntries.length > 0`)
- **Property (P)**: Желаемое поведение — вместо имён и машин соперников показывать только количество записавшихся
- **Preservation**: Неизменное поведение — собственная заявка игрока, логика записи/отмены, отображение решётки в `RaceResults.tsx`
- **EntryButton**: Подкомпонент внутри `RaceCenter.tsx`, отвечающий за UI записи на гонку и отображение заявок
- **getEntryLabel()**: Функция в `RaceCenter.tsx`, возвращающая строку «Имя игрока — Название машины» по записи `RaceEntry`
- **otherEntries**: Массив заявок других игроков на конкретную гонку (`entries.filter(e => e.race_id === raceId && e.player_id !== playerId)`)

## Детали бага

### Условие бага

Баг проявляется в двух местах компонента `EntryButton`:
1. Когда игрок уже записан на гонку — блок «Стартовая решётка» отображается рядом с его заявкой
2. Когда игрок ещё не записан — блок «Стартовая решётка» отображается рядом с кнопкой «ЗАПИСАТЬСЯ»

В обоих случаях вызывается `getEntryLabel(e)`, которая раскрывает имя игрока и название машины.

**Формальная спецификация:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type { phase: string, raceId: string, playerId: string, entries: RaceEntry[] }
  OUTPUT: boolean
  
  otherEntries := entries.filter(e => e.race_id = raceId AND e.player_id ≠ playerId)
  
  RETURN phase = "RACE_DAY"
         AND length(otherEntries) > 0
END FUNCTION
```

### Примеры

- Игрок A записался на гонку «Монца». Игрок B открывает гонку и видит: «• Игрок A — Ferrari 308 GTB». **Ожидается**: «Записано: 1»
- Игрок A и C записались. Игрок B видит: «Стартовая решётка: • Игрок A — Ferrari 308 GTB, • Игрок C — BMW M3». **Ожидается**: «Записано: 2»
- Игрок B записался сам. Он видит свою заявку «✔ Porsche 911» + «Стартовая решётка: • Игрок A — Ferrari 308 GTB». **Ожидается**: «✔ Porsche 911» + «Записано: 1»
- Никто кроме игрока B не записался. **Ожидается**: блок с количеством не отображается (как и сейчас — `otherEntries.length === 0`)

## Ожидаемое поведение

### Требования к сохранению

**Неизменное поведение:**
- Собственная заявка игрока (название машины + кнопка отмены ✕) продолжает отображаться
- Логика записи на гонку (`submitRaceEntry`) и отмены заявки (`supabase.delete`) не затрагивается
- Проверка дублирования машин в разных гонках продолжает работать
- Компонент `RaceResults.tsx` продолжает показывать полную стартовую решётку после начала гонки
- Выбор машины из гаража с фильтрацией по требованиям гонки не затрагивается
- Логика платных гонок и категорий мощности (World Series) не затрагивается

**Область изменений:**
Все входные данные, НЕ связанные с отображением заявок других игроков в фазе `RACE_DAY`, остаются полностью незатронутыми. Это включает:
- Фазы, отличные от `RACE_DAY`
- Отображение собственной заявки игрока
- Логику записи/отмены
- Компонент `RaceResults.tsx`

## Гипотеза о корневой причине

Это не ошибка в логике, а отсутствие ограничения на отображение данных. Причина проста:

1. **Преждевременное раскрытие данных**: Функция `getEntryLabel()` вызывается для `otherEntries` прямо в фазе `RACE_DAY`, хотя эти данные должны быть скрыты до фазы `RACING`
2. **Два дублирующихся блока**: Блок «Стартовая решётка» рендерится в двух ветках `EntryButton` — и когда игрок записан (`myEntry && myCar`), и когда не записан (рядом с кнопкой «ЗАПИСАТЬСЯ»). Оба блока нужно заменить

Корневая причина — отсутствие проверки фазы перед отображением деталей заявок соперников. Данные загружаются корректно (для логики гонки), но UI не должен их раскрывать на этапе записи.

## Корректностные свойства

Property 1: Bug Condition — Скрытие деталей заявок соперников

_Для любого_ состояния, где фаза равна `RACE_DAY` и есть заявки других игроков (`otherEntries.length > 0`), исправленный компонент `EntryButton` НЕ ДОЛЖЕН отображать имена игроков и названия машин соперников, а ДОЛЖЕН отображать только количество записавшихся (текст «Записано: N»).

**Валидирует: Требования 2.1, 2.2**

Property 2: Preservation — Сохранение собственной заявки и прочего поведения

_Для любого_ состояния, где условие бага НЕ выполняется (нет заявок соперников, или фаза не `RACE_DAY`), исправленный компонент ДОЛЖЕН вести себя идентично оригинальному — собственная заявка игрока отображается, логика записи/отмены работает, `RaceResults.tsx` не затронут.

**Валидирует: Требования 3.1, 3.2, 3.3, 3.4, 3.5**

## Реализация исправления

### Необходимые изменения

Исходя из анализа корневой причины:

**Файл**: `components/RaceCenter.tsx`

**Компонент**: `EntryButton`

**Конкретные изменения**:

1. **Замена блока «Стартовая решётка» (ветка «игрок записан»)**: В ветке `if (myEntry && myCar)` заменить блок:
   ```tsx
   {otherEntries.length > 0 && (
     <div className="mt-1">
       <div className="text-[7px] text-[#888] mb-0.5">Стартовая решётка:</div>
       {otherEntries.map(e => (
         <div key={e.id} className="text-[7px] text-[#aaa]">• {getEntryLabel(e)}</div>
       ))}
     </div>
   )}
   ```
   на:
   ```tsx
   {otherEntries.length > 0 && (
     <span className="text-[7px] text-[#888]">Записано: {otherEntries.length + 1}</span>
   )}
   ```
   ("+1" учитывает самого игрока)

2. **Замена блока «Стартовая решётка» (ветка «игрок не записан»)**: В ветке рядом с кнопкой «ЗАПИСАТЬСЯ» заменить аналогичный блок на:
   ```tsx
   {otherEntries.length > 0 && (
     <span className="text-[7px] text-[#888]">Записано: {otherEntries.length}</span>
   )}
   ```

3. **Не трогать**: Функцию `getEntryLabel()`, массив `allPlayers`, загрузку `fetchPlayers` — они могут использоваться в других местах и понадобятся для `RaceResults`.

4. **Не трогать**: `RaceResults.tsx` — там стартовая решётка отображается корректно (после начала гонки).

## Стратегия тестирования

### Подход к валидации

Стратегия тестирования следует двухфазному подходу: сначала подтвердить наличие бага на неисправленном коде, затем проверить корректность исправления и сохранение существующего поведения.

### Исследовательская проверка условия бага

**Цель**: Подтвердить наличие бага на неисправленном коде. Убедиться, что `EntryButton` действительно рендерит имена и машины соперников.

**План тестирования**: Отрендерить `EntryButton` с моковыми данными (фаза `RACE_DAY`, несколько заявок от разных игроков) и проверить, что в выводе присутствуют имена игроков и названия машин.

**Тест-кейсы**:
1. **Записанный игрок видит соперников**: Рендер с `myEntry` + `otherEntries` — проверить наличие текста «Стартовая решётка» и имён (провалится на неисправленном коде — покажет имена)
2. **Незаписанный игрок видит соперников**: Рендер без `myEntry` + `otherEntries` — проверить наличие текста «Стартовая решётка» (провалится — покажет имена)
3. **Нет соперников**: Рендер с `otherEntries = []` — блок не должен отображаться (пройдёт на обоих версиях)

**Ожидаемые контрпримеры**:
- В неисправленном коде: строки вида «• Игрок A — Ferrari 308 GTB» присутствуют в DOM
- После исправления: только текст «Записано: N»

### Проверка исправления (Fix Checking)

**Цель**: Убедиться, что для всех состояний с условием бага исправленный компонент показывает только счётчик.

**Псевдокод:**
```
FOR ALL input WHERE isBugCondition(input) DO
  rendered := EntryButton_fixed(input)
  ASSERT NOT contains(rendered, otherPlayerName)
  ASSERT NOT contains(rendered, otherCarName)
  ASSERT contains(rendered, "Записано: " + count(otherEntries))
END FOR
```

### Проверка сохранения (Preservation Checking)

**Цель**: Убедиться, что для всех состояний без условия бага поведение не изменилось.

**Псевдокод:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT EntryButton_original(input) = EntryButton_fixed(input)
END FOR
```

**Подход к тестированию**: Property-based тестирование рекомендуется для проверки сохранения, так как:
- Автоматически генерирует множество тест-кейсов по всему домену входных данных
- Ловит граничные случаи, которые ручные тесты могут пропустить
- Даёт сильные гарантии неизменности поведения для всех не-баговых входов

**План тестирования**: Зафиксировать поведение неисправленного кода для случаев без заявок соперников, затем написать property-based тесты, подтверждающие идентичность.

**Тест-кейсы**:
1. **Сохранение собственной заявки**: Проверить, что после исправления собственная заявка (название машины + кнопка ✕) отображается как раньше
2. **Сохранение кнопки записи**: Проверить, что кнопка «ЗАПИСАТЬСЯ» работает корректно
3. **Сохранение проверки дублей**: Проверить, что машина не может быть заявлена на две гонки одновременно
4. **Сохранение пустого состояния**: Проверить, что при отсутствии заявок соперников ничего лишнего не отображается

### Юнит-тесты

- Рендер `EntryButton` с `otherEntries` — проверка отсутствия имён и наличия счётчика
- Рендер `EntryButton` без `otherEntries` — проверка отсутствия блока счётчика
- Рендер `EntryButton` с собственной заявкой — проверка наличия названия машины и кнопки отмены
- Проверка корректности числа в счётчике (с учётом +1 для записанного игрока)

### Property-Based тесты

- Генерация случайных наборов `otherEntries` (0-10 записей) — проверка, что имена и машины никогда не отображаются в фазе `RACE_DAY`
- Генерация случайных состояний без условия бага — проверка идентичности вывода оригинального и исправленного компонента
- Генерация случайных комбинаций (записан/не записан × есть соперники/нет) — проверка корректности счётчика

### Интеграционные тесты

- Полный флоу: запись на гонку → проверка скрытия соперников → переход в `RACING` → проверка отображения решётки в `RaceResults`
- Запись и отмена заявки — проверка обновления счётчика
- Несколько игроков записываются последовательно — проверка корректности счётчика
